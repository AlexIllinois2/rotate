## 项目：AppRotate（hahahaxu1/AppRotate）新增「全局强制旋转」功能

仓库不在 GitHub 直连范围内：`git clone https://github.com/...` 失败，改用
`curl https://codeload.github.com/hahahaxu1/AppRotate/zip/refs/heads/main` 下载 zip 解压可用（记住这条路）。

### 用户确认的三个设计决策
1. 全局档位 vs 按应用规则 → **按应用规则优先**（进入已配置应用时暂停全局，离开后回到全局档位，而不是回到"接管全局之前"的快照）。
2. 自动档的方向监听放在**无障碍服务内**（项目无前台服务、无常驻通知；代价是服务被杀则自动档失效）。
3. 固定档包含 0°：共 0/90/180/270 四档。

### 实现
- 新增 `GlobalRotation.kt`：`GlobalRotationMode` 枚举（follow / auto_360 / auto_270 / auto_180 / lock_0 / lock_90 / lock_180 / lock_270）+ `GlobalRotation` 执行器（接管/还原/暂停/自愈）。
- 新增 `OrientationWatcher.kt`：OrientationEventListener + 允许集合收敛 + 250ms 防抖 + 写 `USER_ROTATION`。
- 关键机制：Android 没有「限制自动旋转范围」的公开开关（由 `config_allowAllRotations` 等设备配置决定），
  所以做法是关掉 `ACCELEROMETER_ROTATION`，自己按允许集合写 `USER_ROTATION`。
- 角度换算依据：`OrientationEventListener` 报的 orientation 与 `Surface.ROTATION_*` 一一对应
  （AOSP 两处公式 `orientation = 90 - round(atan2(-Y,X))` 与 `nearest = (atan2(-x,y) + 45)/90` 对同一姿态同解）。
- 踩到的坑（已修）：关掉自动旋转后 `USER_ROTATION` 立刻变权威值，apply 时必须先把它对齐到当前真实角度，否则屏幕会先跳一下。
- `AppPrefs` 增 `global_mode` / `global_base_auto` / `global_base_user`（-1 表示未接管）；`RotationConfig` 增 `globalMode`。
- `RotationController.restore/resetAll` 在全局接管时回到全局状态；服务 `onServiceConnected` 落实档位、`healGlobal` 自愈被改掉的设置。
- `MainScreen` 顶部加「全局旋转」卡片 + 选择弹窗；`MainActivity` 增 `--es gmode` 自动化入口。
- README / docs/notes.md 已同步（用法、权限依赖、已知限制、自测清单 12–17 项）。

## 补充：用户反馈「QQ 180 度没效果 / shizuku 权限没了」（同日）

### 排查结论（模拟器上复现了成因）
1. **无障碍服务没绑定时，一切规则都不触发。** 实测 `am force-stop` 会让
   `dumpsys accessibility` 变成 `Bound services:{}` 且不自动恢复；必须 toggle
   `accessibility_enabled 0→1` 才重新绑定。真机上覆盖安装/省电清理同理。
2. **前台应用自己声明 PORTRAIT 时，「系统设置」方式完全无效** —— 这是 QQ 没效果的最可能原因。
   实测：桌面(Lawnchair, SCREEN_ORIENTATION_PORTRAIT)在前台时，写 user_rotation 1/2/3 屏幕都不动；
   换成 Settings(UNSPECIFIED) 写 2 马上转到 180°。QQ 属于同类。
3. **Shizuku 运行期引擎（`wm fixed-to-user-rotation`）是支持 180° 的**，
   旧文档里「Shizuku 只支持竖屏/横屏」说的是已被取代的 compat 覆盖方案（现为死代码），已修正文档。
4. MuMu 上悬浮窗方式对 PORTRAIT 硬锁应用也推不动（Android 15，`mAllowAllRotations=false`），
   与项目 README 在真机（Nubia/Android 16）上的结论相反 —— 可能是模拟器特性，真机待验。

### 本次改的代码
- `RotationAccessibilityService`: 新增 `verifyLock()` —— 写入系统设置后 1.2 秒复查屏幕角度，
  没变就弹 `warn_lock_ineffective`（提示改用悬浮窗/Shizuku）；`applyShizuku` 前检查
  Shizuku 是否就绪，不可用弹 `warn_shizuku_not_ready`。
- `strings.xml` 新增两条提示文案。
- 实测验证：Settings(跟随系统)+180° → 生效且不误报；桌面(自锁竖屏)+180° → 无效并正确报警。
- 修正 `docs/notes.md` 中 Shizuku「只支持竖屏/横屏」的过时描述，并新增
  「设了方向但屏幕没反应先查这三样」排查段。

## 锁定方式改为全局唯一（用户明确要求）

用户原话：「不对 应该是整个app的设置里只有一个地方设置旋转方式，没有各用各的道理」。
起因：全局旋转设 180° 对 QQ 无效，而单独给 QQ 配「反向竖屏 + Shizuku」有效；
原来的设计是**每个应用各选一种锁定方式**，全局旋转写死走「系统设置」，所以全局永远掰不动硬锁应用。

### 改动
- `AppPrefs`：删掉 per-app 的 `engines` 映射，改成应用级 `KEY_ENGINE`（`engine()` / `setEngine(ctx, kind)`）。
  做了**一次性迁移**：首次读取时把旧 `engines` 映射里用过的那种方式搬过来，不让用户莫名退回系统设置。
  `EngineKind` 加了 `desc` 字段（UI 直接复用）。
- `GlobalRotation`：**按 `AppPrefs.engine` 分三条通道落地**。
  - SETTINGS：关自动旋转 + 写 USER_ROTATION（原行为）。
  - OVERLAY：0×0 悬浮窗；自动档 = 跟着姿态改窗口的 `screenOrientation`，**完全不碰系统设置**。
  - SHIZUKU：shell 写 user_rotation + `wm fixed-to-user-rotation enabled`（支持 180°）。
  `pause()` / `release()` / `heal()` 都按引擎分通道；SHIZUKU 的阻塞调用全部走 `GlobalRotation.worker` 单线程池。
- `OrientationWatcher`：`onApplied` 从 `(Int)->Unit` 改成 `(Int)->Boolean`（由调用方按引擎落地，
  失败则保留候选下次再试）；watcher 自己不再写 Settings。
- `LockNotification`：抽出 `post()`，新增 `showGlobal(context, modeLabel)`。
- `ShizukuRotation.cleanupStaleForce`：全局 Shizuku 接管期间不能把 `fixed-to-user-rotation` 当残留清掉。
- 新增 `AppPrefs.globalBaseFixed` / `KEY_GLOBAL_BASE_FIXED`（Shizuku 方式还原用）。
- UI（`MainScreen`）：新增 `LockEngineCard`（FilterChip 三选一）；权限卡片改成**按当前引擎显示**
  （SETTINGS→修改系统设置；OVERLAY→悬浮窗+通知；SHIZUKU→Shizuku 卡片带「去授权」）；
  `GlobalRotationCard`/`Dialog` 用 `engineWarning()` 指出缺哪个权限并有对应授权按钮
  （修掉用户说的「看不见哪里给 shizuku 权限」）；单应用对话框只选方向，不再有方式三选一。
- 自动化入口：`--es engine` 从 per-app 变成应用级；新增 `--es gmode` 仍可用。

### 关键设计决定
- `pause()` 只对 OVERLAY 撤窗口。SETTINGS/SHIZUKU 都是靠写 `user_rotation` 生效，
  按应用规则直接覆盖即可；尤其 SHIZUKU 撤了再开会和按应用路径抢同一个 `fixed-to-user-rotation`，
  两个不同线程池还会产生竞态（曾考虑撤掉，最终定为不动）。
- 编译校验：`compileDebugKotlin` 通过（未构建 APK、未安装，遵守「禁止自动构建」规则）。

## 全局旋转 × 统一锁定方式 · MuMu 实测（19:35–19:50）

构建 + 安装 debug 包到 MuMu(127.0.0.1:16416) 跑了 `tools/test-global-engine.sh`（新建脚本，
走 MainActivity 自动化入口，不点 UI）。

**通过的用例**：A(系统设置+180°→转)、B(系统设置+桌面硬锁→不动，符合预期)、
C(**悬浮窗+180°→转，且 accelerometer_rotation=1 / user_rotation=0 完全没被动过**)、
E(切回 follow 精确还原)、G(运行中换方式)、Shizuku 未就绪时正确降级(`applied=false`)、
悬浮窗常驻通知文案「全局旋转已生效：锁定 180°（反向竖屏）」。

**实测发现并修掉的两个真 bug**：
1. `RotationController.resetAll()` 兜底分支（没有按应用会话、但全局在接管）不还原系统设置快照
   → 改成 `GlobalRotation.release()` + `reapplyGlobal()`。
2. `GlobalRotation.release()` 只还原"当前方式"写下的东西 → 从系统设置切到悬浮窗时系统设置没人还原
   → 抽出与方式无关的 `restoreSettingsSnapshot()`。
（`RotationController.switchEngine(context, kind)` 也抽出来给 UI 和自动化入口共用。）

**模拟器特性（别误判成产品 bug）**：
- `settings put secure accessibility_enabled 0` 会把 `enabled_accessibility_services` 清成 null，
  必须显式写回组件名才能重新绑定。
- `am start` 在 Activity 已在前台时不保证投递新 intent，会延迟到下一条命令 —— 必须冷启动才稳。
- SharedPreferences `apply()` 要等 Activity 停后台才 flush，读配置前先按 HOME。
- `dumpsys window displays` 是 `ROTATION_180` 符号名，不是索引。
- MuMu 负载高时 WindowManager 极慢（`addView` 观察到 11 秒、单帧 13 秒），脚本等待要放宽。
- **Shizuku 装不上（网络受限）**，改为手动跑同三条 shell 命令验证机制：`adb shell` 与 Shizuku UserService
  同为 uid=2000(shell)，命令本身有效（桌面→90°、设置→180°）；只有"桌面+180°"被 `mAllowAllRotations=false` 挡。
- 悬浮窗对硬锁应用的压制在 MuMu 上不稳定（窗口每次都挂上，但角度有时不跟随），需真机确认。
