# 旋转锁定 AppRotate

按应用锁定屏幕方向的 Android 小工具（目标机型 Android 16 / API 36）。
**不联网、不读取屏幕内容**——核心只有一个无障碍服务在系统需要时被绑定；另有两个默认开、可随时在界面关掉的可选开关：
「开机自启动」（重启手机后自动恢复运行）和「后台守护」（一条低优先级常驻通知的前台服务，进程被系统杀掉后自动重启）。

## 它做什么

给指定的应用单独指定一个方向，进入时锁定、离开时还原。**锁定方式整个应用只有一处设置**（主界面顶部的
「锁定方式」卡片），按应用锁定与全局旋转共用同一种：

| 方式 | 做法 | 代价 |
|---|---|---|
| **系统设置**（默认） | 关掉自动旋转 + 写入 `USER_ROTATION`，离开时按进入前的快照精确还原 | 需要「修改系统设置」权限，动的是系统设置 |
| **悬浮窗** | 加一个 0×0 的 `TYPE_APPLICATION_OVERLAY` 透明窗口，只给它固定 `screenOrientation`；**完全不改系统设置** | 需要「显示在其他应用上层」+ Android 12+；锁定时通知栏常驻一条提示 |
| **Shizuku 强制** | 用 Shizuku 以 shell 身份改旋转设置并打开显示级 `fixed-to-user-rotation`，连"自己写死方向"的应用也能掰动 | 需要装并运行 Shizuku；四个方向 + 保持进入时都支持 |

方向支持：**固定档** 锁定竖屏 / 锁定横屏 / 锁定反向竖屏 / 锁定反向横屏 / 保持进入时的方向；**自动档**（跟全局自动档同一套方向监听，在允许轴内跟重力感应翻转）竖屏自动（0°/180°） / 横屏自动（90°/270°） / 自动（0°/90°/270°） / 全自动（四方向）。横屏应用想自动翻转选「横屏自动」；注意「系统设置」方式下自动档掰不动清单里锁死方向的应用，需要悬浮窗或 Shizuku 方式。

> 早期版本是"每个应用各选一种方式"，后来统一了：同一次锁定里两套机制会互相打架，
> 而且用户记不住"哪个应用用了哪种方式"。升级时会自动把旧配置里用过的那种方式搬过来。

### 全局强制旋转

除了按应用配置，还可以对所有应用强制一个旋转档位（主界面顶部的「全局旋转」卡片）：

| 档位 | 行为 |
|---|---|
| 跟随系统 | 不接管，系统原本怎么转就怎么转 |
| **360° 自动**（可上下颠倒） | 0° / 90° / 180° / 270° 四个方向都跟重力感应转 |
| **270° 自动**（不可上下颠倒） | 转 0° / 90° / 270°；倒过来拿时保持不动 |
| **180° 自动**（跟随应用方向） | 允许上下颠倒，轴跟着应用自身方向走：竖屏应用在 0°/180° 间翻转；应用自己转到横屏（全屏视频、横屏游戏）后在 90°/270° 间翻转；横着拿不会把竖屏应用掰成横屏 |
| 锁定 0° / 90° / 180° / 270° | 固定角度，不跟传感器 |

已单独配置过方向的应用仍然以它自己的规则为准（进入时用它的规则、离开后回到全局档位）。

**横屏让路**：全局档位不会压住应用自己要的方向。前台 Activity 在清单里请求了横屏或全方向旋转（横屏游戏、视频应用的全屏画面）时，全局档位自动暂时收掉、还原成接管前的原生设置，切回竖屏活动或桌面再恢复接管；「180° 自动」在悬浮窗 / Shizuku 方式下除外——这两种方式应用的方向请求到不了显示层，改为把轴切到应用的自身方向（横屏族应用在横屏轴内跟姿态翻转）。应用运行中动态请求横屏（比如点全屏按钮）清单里看不到：180° 自动靠"轴收养"——应用把屏幕转到另一轴时自动档跟着切轴、转回来时收回来；其余自动档靠"实际角度礼让"——屏幕不在允许集合里就不写，等应用自己转回来。

自动档的原理：Android 没有"限制自动旋转范围"的公开开关——能转哪几个方向由 `DisplayRotation` 的
`config_allowAllRotations` 等设备配置决定。所以这里由本应用监听方向传感器、按允许集合决定方向，
**服务被关掉时自动档会停止跟随**，固定档不受影响。
按锁定方式的不同，落地的通道也不同：

| 方式 | 自动档怎么落地 | 固定档怎么落地 |
|---|---|---|
| 系统设置 | 关掉系统自动旋转，按姿态写 `USER_ROTATION` | 关掉自动旋转 + 写死 `USER_ROTATION` |
| Shizuku | 同上，但用 shell 身份写；额外打开 `wm fixed-to-user-rotation enabled` | 同左，一次命令生效 |
| 悬浮窗 | **不动系统设置**，按姿态改覆盖层窗口的 `screenOrientation` | 覆盖层固定一个 `screenOrientation` |

**前台感知的两个来源**（知道"当前前台是哪个应用"才能做按应用锁定、横屏让路、轴切换）：

| 来源 | 适用方式 | 说明 |
|---|---|---|
| 无障碍事件 | 悬浮窗 / 系统设置 | 实时、带 Activity 组件名 |
| UsageStats 轮询 | Shizuku | 500ms 轮询"最近的 Activity resumed"，**`PACKAGE_USAGE_STATS` 权限由 Shizuku 自动 `pm grant` 授予**，整个 Shizuku 链路不再依赖无障碍服务开关 |

前台来源不可用时（无障碍被关 / Shizuku 方式缺「使用情况访问」权限），守护服务会在通知栏提示；
「跟随应用方向」此时强制留在竖屏轴——最坏情况是横屏应用被压住，而不是整个系统被锁进翻转。

> 「系统设置」方式下如果设了 180° 而某个应用不转（比如 QQ），那是它自己在清单里锁死了方向——
> 把锁定方式换成「悬浮窗」或「Shizuku 强制」，全局旋转和按应用锁定会一起跟着变。

### 为什么会有三种方式

Android 没有"按应用设置旋转方向"的公开 API，而"应用自己在清单里写死了方向"时，改系统设置是掰不动它的。
三种方式分别对应不同的可行性边界，细节（含 AOSP 源码依据）见 [`docs/notes.md`](docs/notes.md)。

## 权限

| 权限 | 用途 |
|---|---|
| 修改系统设置（WRITE_SETTINGS） | 仅「系统设置」方式：读写方向与自动旋转（含全局旋转的档位） |
| 无障碍服务 | 只用来识别当前前台是哪个应用（配置里 `canRetrieveWindowContent=false`）——仅悬浮窗/系统设置方式需要；「全局旋转」的**自动档**方向监听也由它常驻承载 |
| 使用情况访问（PACKAGE_USAGE_STATS，AppOps 型） | 仅 Shizuku 方式：前台感知改走 UsageStats 轮询，**由 Shizuku 自动授权**，无需用户操作 |
| 显示在其他应用上层（SYSTEM_ALERT_WINDOW） | 仅「悬浮窗」方式的 0×0 覆盖层窗口 |
| 通知（Android 13+） | 仅「悬浮窗」方式锁定时通知栏的常驻提示 |
界面上只会显示**当前锁定方式需要的那几项权限**，缺哪个就把对应的授权入口摆出来。
| `<queries>` MAIN/LAUNCHER + HOME | 列出可启动应用、识别"回到桌面"（不用 QUERY_ALL_PACKAGES） |

Shizuku 不是本应用的权限：它是独立应用，本应用只通过它的 API 借 shell 身份执行命令（`dev.rikka.shizuku:api`）。

## 构建

要求：JDK 17+（本项目用 21）、Android SDK 36、Gradle 8.11.1、Kotlin 2.1.20 / AGP 8.9.1。

```bash
# 用你本机的 SDK：在仓库根目录建 local.properties
echo sdk.dir=/path/to/Android/sdk > local.properties

# debug（带调试检查，验证脚本要用）
gradle assembleDebug

# release（日常使用；本仓库的脚本用 debug keystore 签名，方便和 debug 包互相覆盖）
gradle assembleRelease
```

`tools/` 里的 PowerShell 脚本是为本机（Windows，工具链装在 `D:\dev\android`）写的，
里面的绝对路径按需改；它们做的事情：

| 脚本 | 作用 |
|---|---|
| `build.ps1` | 设好环境变量后调 Gradle，并把产物同步到 `dist\` |
| `make-icon.ps1` | 从 `icon\rotate.png` 生成启动图标（各密度 mipmap + 自适应图标前景） |
| `verify-device.ps1` | 真机/模拟器端到端验证（见下） |
| `wireless-adb.ps1` | 无线 adb 配对 / 连接 |
| `install-shizuku.ps1` | 下载并安装 Shizuku 官方 APK（「Shizuku 强制」方式用） |

## 已知限制

- **悬浮窗方式需要 Android 12+**：Android 11 及更早把应用覆盖层放在 `NonAppWindowContainers` 里，
  那个容器的 `getOrientation()` 恒返回 `UNSET`，覆盖层的固定方向不参与方向决策。
- **大屏（最小宽度 ≥ 600dp）**：系统默认开启 `ignore-orientation-request`，固定方向请求会被整个丢掉，悬浮窗方式失效。
- **Shizuku 每次开机要手动启动一次**（非 root 设备），且厂商省电可能把它的 server 进程杀掉；这时「Shizuku 强制」不生效。
- **覆盖安装 APK 会停掉无障碍服务**（系统行为），悬浮窗/系统设置方式装完要在应用里重新打开；**Shizuku 方式不受影响**（前台感知走 UsageStats 轮询，不依赖无障碍）。
- 「系统设置」方式离开时还原的是"进入那一刻"的设置；**在目标应用内手动改过旋转，离开时也会被还原**（行为可预期）。
- **全局旋转的自动档依赖前台来源可用**：悬浮窗/系统设置方式靠无障碍服务常驻（被杀后屏幕停在最后的角度不再跟随）；Shizuku 方式靠 UsageStats 轮询（守护服务承载，无障碍被关也照常工作）。前台来源不可用时「跟随应用方向」强制留在竖屏轴，固定档不受影响。
- **自己写死方向的应用，全局档位一样掰不动它**：「系统设置」方式无法把硬锁应用掰到别的方向（横屏游戏在 180° 自动下也只是保持横屏，翻转不了）；「悬浮窗 / Shizuku 强制」方式下 180° 自动能把硬锁应用在自己轴内翻转。想给硬锁应用强制指定别的方向时，给它单独配「悬浮窗」或「Shizuku 强制」。
- **动态请求横屏只有"轴收养 / 角度礼让"一层兜底**：系统真的把屏幕转出去了才会跟随。个别 ROM 在旋转锁定时直接忽略这类请求，屏幕根本不动——这种场景下应用的横屏仍会被压住，可在应用内给它配「保持进入时的方向」绕开。
- 全局自动档有 250ms 防抖；手机平放（接近水平）时 `OrientationEventListener` 返回 `ORIENTATION_UNKNOWN`，不会误转。
